# OpenAPI contract for the RefundFlow API

## Status and scope

This specification defines how the RefundFlow FastAPI application publishes and maintains its HTTP API contract. The FastAPI application is the source of truth: the OpenAPI document must be generated from the application and its Pydantic models, not maintained as a separate hand-authored contract.

The implementation covered by this spec must:

- Describe every supported API operation, including request parameters, request bodies, response models, status codes, and authentication requirements.
- Publish a downloadable OpenAPI document and interactive documentation.
- Check a version-controlled OpenAPI document into the repository for use with Postman.
- Test that the published and checked-in documents accurately represent the application.

This spec does not change API business behavior, replace Entra token validation, or include Azure Blob Storage's signed upload endpoint in the API contract. The browser's direct upload to the URL returned by the API is an interaction with Azure Blob Storage, not an API operation.

## API identity and versioning

- OpenAPI title: `RefundFlow API`.
- OpenAPI `info.version`: `0.1.0` until the application version is deliberately changed.
- API resource routes remain under the existing `/v1` prefix. Health checks remain at `/health/live` and `/health/ready`.
- Versioning the path (`/v1`) is distinct from the OpenAPI `info.version`. A change to a request or response contract must update the checked-in document and generated types. A breaking API contract change requires an explicit API versioning decision; it must not be hidden by silently changing only `info.version`.
- Give the API and its tags concise descriptions suitable for both developers and generated tooling. Do not place credentials, tenant-specific secrets, or internal infrastructure details in the public document.

## Publication and generated artifacts

The following endpoints must be available in local, staging, and production environments:

| Path | Purpose |
|---|---|
| `/openapi.json` | Public, downloadable JSON OpenAPI document generated by the running FastAPI application. |
| `/docs` | Public Swagger UI backed by `/openapi.json`. |
| `/redoc` | Public ReDoc UI backed by `/openapi.json`. |

These endpoints describe the API but do not grant access to protected operations. Do not include secrets or sensitive example data in the schema or examples.

Commit the generated document at `backend/openapi/openapi.json`. Provide a documented, repeatable command that regenerates it from `api.main:app` and fails visibly if the application cannot produce a schema. The running `/openapi.json` response and the checked-in artifact must be semantically equivalent. Do not edit the artifact by hand. Document how to import the running endpoint or checked-in document into Postman.

The checked-in schema must be refreshed whenever an API contract change is made. CI verifies that the schema artifact matches the running application.

## Contract conventions

- Use the existing FastAPI and Pydantic request and response models as the schema source.
- Assign a stable, unique `operationId` to every operation. Renaming one is a generated-client compatibility change and must be reviewed.
- Add summaries and useful descriptions to every operation, parameters, request bodies, and response. Use descriptions to explain role requirements and meaningful business constraints.
- Group operations with explicit tags and tag descriptions. Use tags by API resource or purpose (`health`, `claims`, `uploads`, `reviews`, `admin`, and `webhooks`); avoid assigning claim-listing and KPI operations to an unrelated tag merely because they share a router.
- Define all path and query parameters, including the `status` query parameter on `GET /v1/claims`, with accurate names, types, optionality, constraints, and examples where useful.
- Document successful response models and status codes, and all known validation, not-found, conflict, and authorization responses for each operation. Document FastAPI's current `{"detail": ...}` error shape for `HTTPException` responses; do not claim a response code is returned unless the implementation can produce it.
- Ensure response schemas accurately represent the actual serialized models and omit fields that are not returned. Avoid broad, untyped `object` responses where a stable schema can be defined without changing runtime behavior.
- Keep examples synthetic and free of real personal information, credentials, or signed URLs.

## Authentication and authorization

Define an HTTP bearer security scheme for the Microsoft Entra access token:

- Scheme type: HTTP `bearer`; bearer format: `JWT`.
- Apply the security requirement per operation to protected routes; do not apply it globally to public health checks or the Stripe webhook.
- Document that deployed requests use an access token for the RefundFlow API audience and that authorization is enforced using the Entra `roles` claim. List the minimum role(s) required by each protected operation (`Customer`, `Reviewer`, and/or `Admin`).
- Document expected `401` responses for missing or invalid tokens and `403` responses when the authenticated user lacks a required role, where applicable.
- Do not model the Entra app roles as OAuth scopes: the current implementation authorizes with the `roles` claim, not OpenAPI OAuth scopes.
- The local development identity fallback is an implementation convenience, not a production authentication mode and not a reason to mark protected operations as unauthenticated.

The Stripe webhook is a separate authentication case. Document its required `Stripe-Signature` header and signature verification behavior on that operation; do not apply bearer-token security to it or misrepresent the signature as a static API key.

## Operation inventory

The OpenAPI document must include and accurately describe at least the following operations. The roles below apply to deployed requests; health checks and the webhook have no Entra bearer requirement.

| Method | Path | Tag | Access | Success |
|---|---|---|---|---|
| `GET` | `/health/live` | `health` | Public | `200` |
| `GET` | `/health/ready` | `health` | Public | `200` |
| `POST` | `/v1/claims` | `claims` | `Customer` | `201` |
| `GET` | `/v1/claims` | `claims` | `Customer`, `Reviewer`, or `Admin` | `200` |
| `GET` | `/v1/claims/{claim_id}` | `claims` | `Customer`, `Reviewer`, or `Admin` | `200` |
| `POST` | `/v1/claims/{claim_id}/uploads` | `uploads` | `Customer` | `200` |
| `POST` | `/v1/claims/{claim_id}/uploads/{document_id}/complete` | `uploads` | `Customer` | `202` |
| `POST` | `/v1/claims/{claim_id}/submit` | `uploads` | `Customer` | `202` |
| `GET` | `/v1/reviews/{claim_id}` | `reviews` | `Reviewer` or `Admin` | `200` |
| `POST` | `/v1/reviews/{claim_id}/decision` | `reviews` | `Reviewer` or `Admin` | `202` |
| `GET` | `/v1/admin/kpis` | `admin` | `Admin` | `200` |
| `POST` | `/v1/webhooks/stripe` | `webhooks` | `Stripe-Signature` validation | `200` |

For each operation, document the actual request and response shapes and its known outcomes, including relevant `400`, `401`, `403`, `404`, `409`, and `422` responses. Do not add operations that are not implemented or expose internal workflow endpoints as part of this API.

## Contract and publication tests

Add backend tests that run without Azure services, network access, or credentials and verify:

1. `GET /openapi.json` returns JSON with OpenAPI 3.x metadata and is semantically equivalent to `app.openapi()`.
2. `GET /docs` and `GET /redoc` are available and reference the published schema.
3. Every operation in the inventory exists exactly once with the intended tag, stable `operationId`, documented success response, and applicable error responses.
4. Protected operations declare bearer security; health operations do not. The webhook documents a required `Stripe-Signature` header and does not declare bearer security.
5. Request and response components cover the API's actual Pydantic models and include validation constraints, such as the claim reason and requested amount.
6. The checked-in schema can be regenerated deterministically from the application. CI should fail when the committed schema is stale.

Keep the existing route behavior tests. Contract tests supplement them; they do not replace endpoint-level checks or require live cloud resources.

## Acceptance criteria

- [ ] The running API serves the current, valid schema at `/openapi.json`; `/docs` and `/redoc` are available in every environment.
- [ ] All operations in the inventory have accurate schemas, stable operation IDs, descriptions, tags, responses, and access requirements.
- [ ] The bearer security scheme reflects Entra JWT authentication and role-based authorization; the Stripe webhook is documented separately.
- [ ] `backend/openapi/openapi.json` is generated from the running application's schema and is semantically equivalent to `/openapi.json`.
- [ ] Backend tests validate publication, contract coverage, and security assignments without requiring cloud dependencies.
- [ ] Postman can import the running schema endpoint or checked-in JSON document.
- [ ] A documented workflow regenerates and checks the schema, and CI detects stale artifacts.
